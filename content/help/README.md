# Writing the in-app guide

The guide at `/help` is built from the MDX files in this folder. This page is
for anyone adding or changing an article. `docs/` stays the technical
handbook; the guide is for the people using the app.

## Where things live

| File | Purpose |
| --- | --- |
| `manifest.ts` | The section order and the `HelpAccess` and entry types. |
| `sections/<section>.ts` | One section each: title, description, who may read it (`public`, `org-admin`, `super-admin`), and its articles in order with titles and one-line summaries. |
| `<section>/<article>.mdx` | The article body. One file per manifest `slug`. |
| `index.generated.ts` | Headings and plain-text search sections for every article. Generated by `npm run help:index`; never edit it by hand. |
| `screenshots.json` | Sizes of captured screens in `public/help/`. Written by the capture script; don't edit by hand. |
| `components/help/mdx.tsx` | How Markdown renders, and the components below. |
| `components/help/HelpLink.tsx` | "Help" links from app screens to an article. |

To add an article:

1. Add an entry to the right `sections/<section>.ts` file (or add a new
   section file and list it in `manifest.ts`).
2. Create the `.mdx` file at the same slug.
3. Run `npm run help:index` to regenerate `index.generated.ts`.
4. Run `npx vitest run tests/unit/help-content.test.ts`. It checks that every
   manifest entry has a file, the generated index is current, every link and
   anchor resolves, every `HelpLink` in the app points at a real article, and
   every screenshot exists.

CI runs `node scripts/generate-help-index.mjs --check`, which fails when an
article changed without regenerating the index. The guide never reads files at
runtime, so the split frontend build (which copies `content/help` and
`mdx-components.tsx` into `frontend/`) renders it without the backend.

### Where new features go

Later features slot into the existing sections: event crew, attendance
confirmation and hackathon email switches into `sections/guests.ts` (with the
guest-side pages in `sections/attending.ts`); judging rounds and the Mentor
Desk into `sections/hackathons.ts`; the mobile app into
`sections/getting-started.ts` and `sections/check-in.ts`. A whole new area,
such as volunteer shifts, gets its own section file listed in `manifest.ts`.
Only add an article when the feature is on the branch you are shipping.

## Article shape

- Don't write a `#` title or a summary line. The page shows both from the manifest.
- Open with one or two sentences saying what the feature is for and when you'd use it.
- Use `##` for main sections (they make up "On this page") and `###` sparingly.
- Put the main task early, as numbered steps inside `<Steps>`.
- End with related links or edge cases ("Good to know"), not a summary.
- Aim for 300 to 900 words. Split the article if it grows much longer.

## Voice

- British English, matching the app: organisation, colour, cancelled, programme.
- Write "Space Works" (two words), never "SpaceWorks". The product is
  "Space Works Events"; "the app" is fine after the first mention.
- Second person, plain words, short sentences. Write for a volunteer organiser,
  not a developer. Explain *why* when a rule might surprise people.
- Name buttons, tabs and fields exactly as the app shows them, in **bold**:
  "Open the **Guests** tab and choose **Approve**." Show menu paths with an
  arrow: "**Settings** → **Webhooks**".
- Describe what people can do, never how the code does it. No file names,
  database fields, environment variables or HTTP routes in public sections.
  Developer, instance and installation sections may name endpoints, scopes,
  settings and commands.
- Never put real-looking secrets, tokens, ticket codes or email addresses in
  examples. Use `ada@example.org` style addresses and obvious placeholders.
- Be exact about limits and rules (sizes, counts, who can do what). If you
  aren't sure the app behaves a certain way, check the code or leave it out.
- No "Oops" or "Something went wrong".

## Components

```mdx
<Steps>

1. Open the event and choose the **Settings** tab.
2. Turn on **Submissions**.

</Steps>

<Callout kind="tip">Short, useful advice.</Callout>
<Callout kind="note">Background worth knowing.</Callout>
<Callout kind="warning">Something that can't be undone, or that surprises people.</Callout>
<Callout kind="permission">Owners and admins, and co-organisers with **Manage registrations**.</Callout>

<Screenshot name="event-dashboard-overview" alt="The event dashboard Overview tab with the readiness checklist" />

Press <Kbd>Enter</Kbd> to print.
```

Leave a blank line inside `<Steps>` and `<Callout>` around Markdown content.
Link to other articles with absolute paths, optionally with a section anchor:
`[Publishing](/help/events/publishing#who-can-find-it)`. Anchors are the
heading text in lower case with hyphens. A public article must not link to an
`org-admin` or `super-admin` one.

A `<Screenshot>` must name a capture listed in `screenshots.json` with its PNG
in `public/help/`. Add the step to `tests/help-screenshots/` first, capture,
then reference it.

## Capturing screenshots

Everything under `public/help/` is served publicly to anyone, signed in or
not, so screenshots must show only the fictional demo data the seed creates:
never a real organisation, person, address, ticket or secret.

The capture seeds fictional demo data (the "Riverside Tech Collective"), so
run it only against a **disposable**, migrated local database: the seed
deletes and recreates its own organisations and users on every run, and
refuses to start without an explicit opt-in.

```sh
HELP_SCREENS_SEED=1 \
HELP_SCREENS_DATABASE_URL=postgresql://localhost:5432/swevents_help_screens \
  npm run help:screenshots
```

It starts `next dev` on port 3124 (`HELP_SCREENS_PORT` to change it), or
reuses a server already running there with the same settings, with
`STAFF_MFA_REQUIRED=false` so the demo staff skip the authenticator check. It
writes `public/help/<name>.png`, updates `screenshots.json`, and clears queued
email so nothing is ever sent. Payment data is seeded directly as fictional
orders, refunds and payouts; no payment provider is ever called. Demo staff
get an authenticator just before the super admin Security screen, as real
staff must, so its MFA figures match a correctly run instance.
